Enhancing the App UI — One Prompt, Done Right

After your app is functional, one pass to make it look like a real product. Brand colours, navigation rail, visible cards, split login, auto-filled forms — all in a single Claude Code prompt.

When to use this guide

You have completed Phase 4. The app is fully functional — login works, requests are created, the API is connected, data lives in PostgreSQL. But the UI looks generic: white backgrounds, invisible text on dark cards, no brand identity.

This guide gives you one single Claude Code prompt that transforms the entire visual experience in one pass. No iterations. No guessing. Run it once on the Flutter project and the app looks like it belongs to Khan Chacha.

👉 Before you run this

Make a copy of your Flutter project folder first. Rename the original to khan_chacha_mrms_backup/. Then run the prompt on the working copy. If anything breaks you have a clean fallback.

What this prompt does

🎉

Khan Chacha brand colours

Deep forest green backgrounds + warm amber/gold accents matching the actual Khan Chacha restaurant brand identity.

☰

Left navigation rail

Replaces the bottom navigation bar with a desktop-appropriate side rail. Home, Requests, New Request — always visible.

🔒

Split login screen

Left panel: Khan Chacha branding, heritage, feature pills. Right panel: compact login form — not full-width fields.

📋

Visible request cards

Every Text widget gets an explicit warm-white colour. Status chips colour-coded. Category icons. Left border stripe per status.

📌

Auto-filled outlet fields

The new request form reads the logged-in user’s outlet and pre-fills Outlet ID, Outlet Name, Address, and Manager Name automatically.

🔄

Dashboard refresh

Status counts reload when returning to the Home tab. A refresh button is also added for manual refresh at any time.

Before
White/grey generic Flutter look. Cards appear empty (dark text on dark background). Bottom navigation bar. Full-width login fields. Outlet fields blank in the form. Dashboard counts go stale.
After
Deep green + gold Khan Chacha identity. Cards show product name, category icon, status chip clearly. Left rail navigation. Split login with branding. Auto-filled outlet fields. Dashboard refreshes on tab switch.

Form Enhancement Reference

Before moving to the next feature phase, here is a reference for how the New Request form should behave after this enhancement. Share this with students so they know what "correct" looks like.

✓ Fields the user fills in (editable)

  • Product Name — free text, required (e.g. "AC Voltas Unit - Main Hall")
  • Product ID — optional, auto-generated as EQ-XXXXXXXX if left blank
  • Category — dropdown: Electrical / AC / Kitchen
  • Description — multi-line, required
  • Image — optional camera/gallery attachment

🔒 Fields auto-filled and read-only (not editable)

  • Request ID — auto-generated as REQ-XXXXXXXX on screen load
  • Outlet ID — from AuthService().currentUser.outletId
  • Outlet Name — from AuthService().currentUser.outletName
  • Outlet Address — looked up from outletId map
  • Manager / Raised By — from AuthService().currentUser.name
  • Status — always Open for new requests, shown informational only

What changed and why it matters

A summary of every meaningful improvement so you can explain each one to students during the session.

Why cards appeared blank

Flutter’s DefaultTextStyle inherits through the widget tree. When ThemeData.textTheme has a dark colour (which happens when the base theme is misconfigured), every Text() widget without an explicit style renders that dark colour on a dark card. The fix: every Text inside a card gets a hardcoded const Color(0xFFF5F0E8) that cannot be overridden by the theme.

Why outlet fields were blank in the form

The form’s initState() didn’t read from AuthService().currentUser. The controllers were created empty and left empty. Adding those four lines to initState() fills them from the already-logged-in user object without any extra API call.

Why the bottom nav was replaced

The app targets Windows desktop. Bottom navigation bars are a mobile pattern designed for thumb reach. On a desktop with a wide screen and a mouse, a left navigation rail is the correct pattern — it uses the vertical space efficiently and matches what users expect from desktop software.

Why the login is split

Full-width text fields on a 1440px wide screen look wrong — the fields stretch too far and the layout looks like a web form from 2005. A constrained 380px form centred on the right panel, with branding on the left, uses the space correctly and looks professional.

Why dashboard counts went stale

initState() runs once when the widget mounts. If the dashboard is part of a rail layout (never unmounted), initState() never runs again when you switch tabs. Calling _loadDashboard() on every return to index 0 in the rail’s onDestinationSelected fixes this completely.

Key lesson for students

The difference between a working app and a polished app is usually not the features — it is the attention to visible details that users actually see. Invisible text, blank forms, and generic layouts do not inspire confidence in a client. These are the fixes that make a demo feel like a real product.
