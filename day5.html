Notification System

Two levels of notifications: in-app (bell icon with badge, works while the app is open) and push (system notification even when app is in background or closed).

🔔 In-app notifications (polling)

A timer runs every 30 seconds and checks the API for changes since the last check. If new requests or status changes are found, the bell icon shows a badge count. Tapping the bell shows a notification list. Works on Windows and Android without any external service.

📲 Push notifications (firebase)

When the app is closed or in the background, push notifications are sent via Firebase Cloud Messaging (FCM). The API sends a push after creating or updating a request. Requires a Firebase project but works on Android and Windows.

How in-app notification polling works

App launches → store last_check timestamp
Timer.periodic(30 seconds) → GET /api/notifications?since=last_check
API queries: new requests (for managers) + status changes on user's requests (for staff)
Returns: [ { id, type, message, requestId, createdAt } ]
Flutter: update badge count → store in local list → show bell badge
User taps bell → NotificationDrawer slides in → mark all as read

Testing Notifications with Android Studio Emulator

You do not need to extract an APK or deploy anything to test notifications. The Android emulator in Android Studio runs a full Android OS on your PC. Flutter treats it exactly like a real phone — you get real system notifications, badge counts, and the notification tray.

Step 1 — Check if an emulator already exists

flutter emulators

If it lists an emulator — you are ready. Skip to Step 3. If the list is empty, continue to Step 2.

Step 2 — Create an emulator in Android Studio

  1. Open Android Studio → Tools → Device Manager
  2. Click Create Virtual Device
  3. Choose Pixel 6 → Next
  4. Select API 34 (Android 14) → Download if needed → Next
  5. Click Finish
  6. Press the play button ▶ next to the device to start it

Step 3 — Critical: Change BASE_URL for emulator

The Android emulator cannot reach localhost — it uses a special IP instead:

// lib/services/api_service.dart
static const String _baseUrl = 'http://10.0.2.2:3000/api';
// 10.0.2.2 is Android emulator's alias for the host machine's localhost

For Windows desktop: use localhost:3000. For emulator: use 10.0.2.2:3000. Switch between them as needed.

Step 4 — Run both server and app

# Terminal 1 — API server
cd khan_chacha_api
npm run dev

# Terminal 2 — Flutter on emulator
cd khanchacha
flutter run -d emulator

Polling vs Real-Time — What comes next

The notification system we built uses polling — the app asks the server every 30 seconds "anything new?" This works well for a demo and for small deployments. But it has real limitations at production scale.

⏳ Limitations of polling

  • 30-second delay is not truly real-time
  • Every device makes an API call every 30 seconds — 20 outlets × 2 users = 40 API calls/minute doing nothing
  • Does not scale well beyond ~50 concurrent users
  • Wastes API and database resources when nothing is happening
  • If the manager’s app is closed — no notification at all

⚡ What real-time requires

  • Server pushes to clients the moment something changes
  • Clients listen, not ask — no wasted calls
  • Push notification delivered even when app is closed
  • Scales to hundreds of users efficiently
  • Standard in enterprise HRMS, ERP, and ops tools

Event-driven architecture — the right long-term solution

Real-time delivery requires an event-driven layer between the API and the app. When a new request is saved to the database, the API publishes an event to a message bus. That bus delivers it to all subscribed clients instantly — no polling needed.

EVENT-DRIVEN FLOW (future architecture)
Flutter form submit → POST /api/requests
Node.js saves to DB → publishes event to Message Bus
   │                    │
Mobile push (FCM)    WebSocket push to open apps
Phone notification tray  Bell badge updates instantly

🌟 Raushan’s suggestion — if you go real-time

Azure Web PubSub + Azure Notification Hubs is the cleanest path if you are already using Azure App Service for the API. All services are in one portal, one bill, one subscription. The Node.js SDK for Web PubSub is simple — publishing an event after a DB write is 3 lines of code. For Khan Chacha’s scale (20 outlets, ~40 users), the free tier of both services covers the entire workload indefinitely. AWS is equally capable but requires more services wired together (SQS + SNS + Lambda or AppSync) — more powerful but more configuration. Stick with Azure if you are already there.

Estimated real-time stack cost on Azure: ₹0–₹1,500/month ($0–$18) depending on message volume. For Khan Chacha, likely free tier for 12+ months.

📋 Note for students

The polling approach we implemented today is production-acceptable for small deployments. Most internal enterprise tools at 20–50 users use polling. Real-time WebSocket infrastructure adds complexity and cost that is only justified when you have hundreds of concurrent users or when seconds of delay genuinely affect operations. For Khan Chacha in Year 1 — polling is perfectly fine. Revisit this decision when the chain expands beyond 50 outlets.

Non-technical staff often write vague descriptions like "not working" or "problem with AC." This feature adds quick-select buttons above the description field. Tapping one inserts a well-structured template that the staff member only needs to fill in the specifics.

Teaching point

The words in [brackets] are the only parts staff need to fill in. Everything else is written for them. This means even a staff member with minimal literacy can raise a clear, useful maintenance request that gives the manager enough information to act.

Migrating to Supabase

Supabase is managed PostgreSQL in the cloud. Migration from local PostgreSQL to Supabase is one .env change on the API server. The SQL schema, queries, and Flutter code need zero changes.

Step-by-step migration

Step 1 — Create a Supabase project

  1. Go to supabase.com → sign in with GitHub
  2. Click New Project
  3. Choose a region (South Asia → Singapore for India)
  4. Set a database password — save it securely
  5. Wait ~2 minutes for the project to be ready

Step 2 — Run your schema on Supabase

  1. In Supabase: go to SQL Editor
  2. Paste the contents of db/schema.sql and run it
  3. Then paste db/seed.sql and run it
  4. Check Table Editor → verify outlets, users, maintenance_requests exist

Step 3 — Get the connection string

In Supabase: Settings → Database → Connection string → URI tab. Copy the string. It looks like:

postgresql://postgres:[YOUR-PASSWORD]@db.xxxxxxxxxxxx.supabase.co:5432/postgres

Step 4 — Update API .env (one change)

DB_HOST=db.xxxxxxxxxxxx.supabase.co
DB_PORT=5432
DB_NAME=postgres
DB_USER=postgres
DB_PASSWORD=[YOUR-SUPABASE-PASSWORD]

Restart the API: npm run dev. Flutter app needs zero changes. Done.

Free tier limitation

Supabase free tier pauses the database after 1 week of inactivity. For a live demo this is fine. For production use, upgrade to Pro ($25/month) which has no pause. Alternatively, send one request per week to keep it active.

Migrating real data from Google Sheets

Once Supabase is set up, follow the Google Sheets migration guide in the Pre-Launch Field Guide. Export the sheet as CSV, run the Claude audit prompt, generate the migration SQL, and run it in the Supabase SQL Editor. The same process, same SQL — just a different target database.

What deploys where

Flutter App

NOT deployed to a server. Compiled to a binary: .apk (Android), .exe (Windows). Distributed directly to devices. The server never runs Flutter.

Node.js API

Deployed to Azure App Service or AWS. Always-on server listening for Flutter's HTTP requests. One change: BASE_URL in api_service.dart points to the live URL.

PostgreSQL Database

Hosted on Supabase (recommended) or AWS RDS. The API's .env points to Supabase. Zero code changes anywhere else.

🌟 Raushan's Recommendation

Use Azure App Service for the Node.js API. Setup takes 10 minutes with the Azure CLI. Environment variables go in the portal — no .env file needed. Free SSL included. The same Azure account your students already use for AZ-204 training works here. Supabase for the database keeps things simple and avoids the VPC/RDS complexity of keeping everything on AWS. This combination — Azure App Service + Supabase — is the fastest path to a live, real URL that students can demo to their managers the same day.
